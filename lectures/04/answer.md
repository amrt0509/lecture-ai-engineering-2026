## 宿題

- 取り組んだレベル：実装
- やったこと：

  3. `tools/annotate.py` を用いて生成された回答に人手で合否ラベル（pass / fail）を付与し、`uv run python -m app.judge --cases data/eval/my_cases.jsonl` でLLM採点器を実行して一致率を算出した。
  4. 判定結果を踏まえ、コードで判定すべき基準とLLMに任せる基準の使い分けについて整理・考察した。
- 結果：
  - 基準別の一致率（10件）：
    - 根拠：6/9（要確認 1件）
    - 範囲：10/10
    - ヒント：10/10
    - 分かりやすさ：10/10
    - 回の表示（コード）：10/10
  - 総合の一致率：5/9（Coverage: 90%）
  - 不一致・要確認の内訳：
    - 根拠（#my_01, #my_02, #my_03）：自分は一般的な説明として正しい知識であるためpassとしたが、LLM採点器はルーブリックの「用語集にない語は『用語集にない』と伝える」というルールを厳格に適用し、断り書きなく説明していたため過検出（LLM=fail, 自分=pass）となった。
    - 要確認（#my_05）：未収録用語「PPO」に対し一般的な説明を行ったため、ルーブリックの未決定事項に該当しunsureと判定された。
  - コードで判定した方がよい基準とLLMに任せる基準の使い分け：
    - 【コードで判定すべき基準】：
      - 「回の表示」のような特定構文・フォーマット（末尾に『第N回』が含まれるか）、出力文字数制限、JSON等のスキーマ検証、禁止語・機密情報のチェック。
      - 理由：決定論的・瞬時に判定可能でコストがゼロに近く、LLM特有のハルシネーションや位置バイアス・長さバイアスを完全に排除できるため。
    - 【LLMに任せる基準】：
      - 「根拠（用語集の定義に反していないか、推測で断定していないか）」、「範囲（指示無視や講座外の質問を役割通り断れているか）」、「ヒント（直接の答えを出さずに考え方を導けているか）」。
      - 理由：文脈やニュアンスの解釈、自然言語の柔軟な言い換えの妥当性を評価する必要があり、完全一致や正規表現などの静的ルールでは判定できないため。
- 気づき・疑問：
  - 人手評価では「大体合っている」と見逃しがちになる部分（用語集未収録であることの事前明記など）を、LLM採点器はルーブリックに忠実に厳格に検出できる強みがあることが分かった。
  - 実務でLLM採点器を安定運用するためには、「分かりやすさ」などの定性的な基準であっても「文字数が〇〇文字以内」「結論から述べているか」など、可能な限り具体的かつ客観的なルーブリックに分解して定義する必要性を実感した。
