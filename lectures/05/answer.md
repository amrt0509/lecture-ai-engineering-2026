  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行し、第2回 p.52（1位）、p.51（2位）、p.60（3位）、p.47（4位）、p.61（5位）の5件が返ることを確認した。

- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - 単一ページ質問では全方式で必要な根拠（p.51-52）を取得し正答できたが、ベクトル検索の下位3件（p.60, 47, 61）や全文投入の他講義ページなど、回答に直接使われないページも同じ単価で入力トークンを消費した。

- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - 基本の方式としては「ベクトル検索」または「Graph」を採用したい。全文投入と比べて入力トークンとAPI費用を約1/20〜1/30に抑えつつ、Treeのようにモデル応答回数（5回・22.69秒）が膨らまず高速に応答できるため。
  - 比較条件の限界：全文投入のみ全9資料（438ページ）が対象で他方式（214ページ）と母集団が異なる点、また1回ずつの計測のためAPIの応答速度の揺らぎが含まれる点。
- 気づき・疑問：
  - 全文投入でも正答自体は可能だが、1クエリあたり約11.7万トークン（$0.035）を消費するため、リクエスト数が増える実運用では検索によるコンテキストの絞り込みがコスト面で不可欠だと実感した。

- 改善した例と、残る失敗・制約：
  - 役立った（根拠が増えた）例：質問2では、変更前は1回目の検索でp.39（コンパクションとメモリ）周辺しか取れず2回目の再検索が必要だったが、変更後はp.39に隣接するp.38・p.40（日々のメモから長期メモリへの選別プロセス）が前後ページ取得で一度に揃った。結果としてツール呼び出しが2回→1回（モデル応答3回→2回）に減り、応答時間（18.17秒→8.01秒）・総入力トークン（6,640→4,566 tokens）・費用（$0.003420→$0.002795）のすべてが改善した。
  - 残る失敗・不要な情報が増えた例：質問1のようにp.51-52だけで根拠が完結する場合でも、下位ヒット（p.47やp.61）の前後ページ（p.46, p.48, p.62の次回予告など）まで機械的に付与されるため、1回の検索あたりの取得ページ数が5件→11件に増え、入力トークン数が約1.78倍（3,028 → 5,376 tokens）、API費用も約22%増加した。また、離れたページ（p.13とp.39など）の関係は前後1ページ拡張だけでは直接たどれない制約が残る。
- 気づき・疑問：
  - 講義スライドのように連続ページで文脈が展開される資料では、前後1ページを同時取得するだけでエージェントの追加検索ループを抑制し、結果的にトータルのレイテンシやトークン消費まで削減できる場合があることが新たな発見だった。
  - 一方で、全検索ヒット（上位5件すべて）に一律で前後ページを付けると単一ページ質問でのノイズ・コスト増につながるため、距離が近い上位1〜2件にだけ前後ページを付与する設計にすれば、両者のトレードオフをさらに最適化できると考えた。
